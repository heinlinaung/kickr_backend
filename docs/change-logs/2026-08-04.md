## The nine changes

### 1. Sign up with a name

`POST /auth/signup` accepts an optional `name` (2–60 chars).

- Supplied → stored, trimmed. Omitted, empty or whitespace-only → falls back to the email's local part (`player@example.com` → `player`).
- **Optional, not required**, so existing clients posting only `email` + `password` keep working.

📄 [auth-api.md §3.1](../api/auth-api.md) · spec [§2](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 2. Group detail returns the caller's role

`GET /groups/:id` now includes `userRole` and `memberStatus`.

```json
{ "userRole": "captain", "memberStatus": "approved" }
```

> ⚠️ **Check `memberStatus`, not just `userRole`.** A pending requester already has `userRole: "member"`, so treating a non-null role as "is a member" shows group content to someone never approved.

`GET /groups` also renamed its `myRole` field to **`userRole`** so both endpoints agree.

📄 [groups-and-locations-api.md §3.4](../api/groups-and-locations-api.md) · spec [§3](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 3. Group gains `country` / `city`; rules reworked

New optional free-text `country` and `city` on the group (indexed, powering change #8). This **reverses** an earlier spec decision to derive them from the attached `Location` — a team's location is a property of the team, not of any one pitch.

Rules changed three times over the course of this work:

1. The **max-3 cap was removed** (no count limit, no per-rule length limit). The cap turned out to live in *three* places, not the two the spec listed.
2. The dedicated `GET`/`POST /groups/:id/rules` routes were **removed** — rules are now just a field on create/update/read. This also required adding the field to `CreateGroupDto`, which had never accepted it, so rules previously could not be set when creating a group.
3. The field was **renamed `teamRules` → `rules`** to match the API text.

**Newlines inside a rule are preserved verbatim**, including blank lines, and non-ASCII (Burmese, emoji) round-trips byte-for-byte. The client must render with `white-space: pre-line` or equivalent — this is the likeliest place for the feature to look broken while the API is correct.

📄 [groups-and-locations-api.md §3.9](../api/groups-and-locations-api.md) · spec [§4](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 4. Group QR is open to any authenticated user

`GET /groups/:id/qr` lost its owner/admin check — any logged-in user can fetch a group's invite link, so ordinary members can share an invite.

Safe **only because of change #6**: a harvested code now creates a pending request rather than granting entry. `GET /groups/:id/invite-code` (which *rotates* the code) stays owner/admin.

> Implementation note: `generateInviteCode` was *also* role-gated, so removing the check from `getQr` alone would still have 403'd a plain member whenever the group's code was missing or expired. Split into a gated rotate path and an ungated mint path.

📄 [groups-and-locations-api.md §3.5](../api/groups-and-locations-api.md) · spec [§5](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 5. Admin force-join endpoints

New `admin` module behind an `x-admin-key` shared secret — **not** a user JWT.

| Method | Path |
|---|---|
| `POST` | `/admin/groups/:groupId/members` |
| `POST` | `/admin/events/:eventId/players` |

Bypass permissions (role checks, approval flow, event lifecycle state) but preserve data integrity (existence, duplicates, capacity). Per-user results with a `200` even when everything is skipped — `200` never means "all added".

**Disabled by default:** `ADMIN_KEY` ships blank in `.env.example` and the endpoints fail closed when it is unset. Treat the key as a root credential — anyone holding it can add any user to any group or event. **Never ship it in the mobile app.**

📄 [admin-api.md](../api/admin-api.md) (new) · spec [§6](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 6. Join by code / QR now requires approval

**`POST /groups/join-by-code` no longer joins immediately.** It creates a `pending` request an owner/admin must approve — identical to request-to-join.

```json
{ "message": "Join request sent. Waiting for approval.", "status": "pending" }
```

Branch on `status`, not the message string. Capacity moved to *approval* time, so a successful call is **not** a guarantee of a free slot.

This resolves the spec's open decision #5, an inconsistency flagged since 2026-07-22.

📄 [groups-and-locations-api.md §3.6](../api/groups-and-locations-api.md) · spec [§6b](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 7. Event detail returns the group's rules

`GET /events/:id` includes `groupRules: string[]` — the parent group's rules, or `[]` for events with no group (never `null`). Read-only projection; rules are edited on the group.

📄 spec [§7.1](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 8. `GET /events?region=` filter

Filters events by the owning group's `country` **or** `city`, case-insensitively — so `region=Myanmar` and `region=Yangon` both work without the client knowing which granularity it holds.

Events with no `groupId` are **excluded** when `region` is set (no group, no region). Composes with the planned `near=`/`radius=` geo filter. Depends on change #3.

📄 spec [§7.2](../superpowers/specs/2026-08-03-pre-events-changes.md)

### 9. Leave a group

New `POST /groups/:id/leave`. Self-service — no approval, and no target id in the path, so it cannot be used to remove anyone else.

| Case | Status |
|---|---|
| `admin` / `captain` / `member` leaves | `200` |
| **Owner** | `403` |
| Not a member / group missing | `404` |

Two behaviours beyond the bare requirement:

- **A pending join request is withdrawn by the same call**, so this doubles as "cancel my request".
- **The owner's block is permanent today** — ownership transfer and group delete both do not exist, so an owner has no way out of their own group at all.

Hide the Leave action for owners rather than surfacing the `403`.

📄 [groups-and-locations-api.md §3.10](../api/groups-and-locations-api.md) · spec [§6c](../superpowers/specs/2026-08-03-pre-events-changes.md)

## Breaking changes

| Change | Impact | Client action |
|---|---|---|
| **Join-by-code requires approval** (#6) | A build that routes into the group on success drops the user into a group they have not joined; every member-only call then `403`s. | Show "request sent — awaiting approval". Poll `GET /groups/:id` → `memberStatus`. |
| **`teamRules` → `rules`** (#3) | Sending `teamRules` is rejected with `400 property teamRules should not exist` (strict whitelist), so the failure is loud rather than silent. | Rename the field. Run the migration. |
| **`myRole` → `userRole`** (#2) | `GET /groups` items no longer carry `myRole`. | Rename. |
| **`/groups/:id/rules` routes removed** (#3) | These now fall through to the `:id` wildcard, so a stale client gets confusing behaviour rather than a clean `404`. | Use the `rules` field on create/update/read. |

## Known gaps — not addressed here

| Gap | Consequence |
|---|---|
| **No notifications for join requests/approvals** | Owners aren't told a request arrived, and requesters aren't told they were approved. With QR joins now needing approval (#6), requests may sit unnoticed. Poll `memberStatus` meanwhile. |
| **No ownership transfer, no group delete** | Why an owner cannot leave (#9). |
| **`GroupMember.level` is inert** | Stored and settable, but nothing reads it; the "plus one" feature it was designed for does not exist. Don't gate UI on it — the semantics may still change. |
| **`rules` is unbounded** | No count or length cap by explicit decision. Mongo's 16 MB document ceiling is the only backstop. |
| **No audit trail on admin endpoints** | One shared key, no attribution of who used it or when. |
| **`role` / `favouriteTeam` / username autogeneration** | Still unimplemented on the user profile. |
| **`GET /locations/search`** | Still unbuilt; the indexes exist. |
