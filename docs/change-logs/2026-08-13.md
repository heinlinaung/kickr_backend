## ⚠️ Before deploying — two required actions

**1. Run the rules migration.** `Group.rules` changed from `string[]` to a single
text block. Existing documents keep arrays that the new schema does **not** read,
so those groups would appear to have no rules at all.

```bash
npx ts-node scripts/migrate-group-rules-to-text.ts           # dry run, writes nothing
npx ts-node scripts/migrate-group-rules-to-text.ts --apply
```

Entries are joined with `\n`, so a group that had three rules comes back as three
lines. Verified on seeded data: interior newlines inside an entry survive, empty
arrays become `""`, and documents already holding a string or no field at all are
skipped. Safe to re-run — a second pass reports "nothing to migrate".

**2. Coordinate the Flutter release.** Three breaking changes need a matching
client build — see [Breaking changes](#breaking-changes).

## Misc

### 1. `group.rules` is now text, not an array

`rules: string[]` → `rules: string`. The API no longer imposes a bullet
structure; the client owns presentation. Newlines are preserved verbatim and
nothing is trimmed, so leading, trailing and interior blank lines all survive.

Render with `white-space: pre-line` (or split on `\n`) — HTML collapses newlines
by default, which is the most likely way this looks broken while the API is
correct.

### 2. Role list in change-role — `member` was already there, `vice-captain` added

The reported gap (`member` missing) turned out not to exist: the DTO already
accepted `member` alongside `admin` and `captain`, and
`GroupsService.updateMemberRole` applied it. Verified end to end — demoting a
captain to `member` succeeds. If it looked missing, it is likely the Flutter
role list rather than the API.

**A new `vice-captain` role was added.** The member role enum is now
`owner | admin | captain | vice-captain | member`.

`vice-captain` carries **exactly captain's permissions**:

| | captain | vice-captain |
|---|---|---|
| Edit a group-owned location | ✅ | ✅ |
| Delete a group-owned location | ❌ | ❌ |
| Act as event organizer | ❌ | ❌ |
| Leave the group | ✅ | ✅ |

A deputy that could not do what the captain does would be surprising, and
editing a venue is reversible. Deleting stays with owner/admin because removing
a pitch the group relies on is structural. Event organizer remains the event's
creator plus the group's owner/admin — unchanged for both roles.

`owner` is still unassignable via this endpoint: a group has exactly one, and
changing it needs an ownership-transfer flow that does not exist yet.

No migration needed — this widens an enum, so existing documents stay valid.

### 3. `GET /events/group/:groupId` hides expired events

Expired events (date before **today**) and `done` events are now excluded by
default — a group screen is about what is coming up, and past fixtures otherwise
pile up at the top forever.

- Expiry is measured by **day**, not timestamp: an event earlier this afternoon
  is still "today" and still listed. Cutting at `new Date()` would drop an event
  from the list while it was being played.
- `done` is excluded regardless of date; an archived event is finished either way.
- `?includeExpired=true` returns everything, for a history view.
- An explicit `?status=done` still returns those events — pinning a status
  overrides the exclusion, or the filter would be unusable.

### 4. `event.duration`

New field, **minutes**, minimum 60, default 90. Settable on create and via
`PATCH /events/:id`. This is what drives fixture generation (below).

### 5. Event detail returns a location object

`GET /events/:id` resolves `locationId` into a `location` object (name, lat/lng,
url, address), so a detail screen renders the venue without a second request.
`locationId` is still returned for clients that only need the id.

### 6. Event detail returns the caller's role

`GET /events/:id` now includes `userRole` — the caller's role in the owning group,
or `null` for a non-member or a groupless event. Only an **approved** membership
counts: a pending request stores `role: 'member'` but confers nothing, so
reporting it would be misleading.

The group's `rules` continue to ride along as `groupRules` (now a string).

## Shuffle update — a two-step team flow

The old `PUT /events/:id/teams` took a finished roster and derived everything from
it in one call. Teams are now created **empty** first, then populated — because
the client shuffles locally and the organizer may hand-edit the result, so
creation and assignment are genuinely separate steps.

### `POST /events/:id/teams/generate`

```
{ "teamsCount": 3, "duration": 30 }
```

Creates that many empty teams (named from the colour vocabulary) and derives the
fixture list from the event's duration:

```
matchCount = floor((event.duration - 10) / duration)
```

Ten minutes come off the top as buffer — warm-up, changeovers, overrun — and the
result is **floored**, so a schedule can never exceed the booked slot. The
response includes a `schedule` breakdown so the client can show how the number
was reached rather than reverse-engineering it.

| `event.duration` | `duration` | Matches |
|---|---|---|
| 90 | 30 | **2** — (90−10)/30 = 2.66 → 2 |
| 100 | 30 | **3** — (100−10)/30 = 3 |
| 60 | 90 | `400` — not even one match fits |

A match longer than the event is refused up front rather than persisting an empty
fixture list the organizer would have to debug.

Re-running replaces the previous teams, fixtures and assignments. That is the
intended way to change the team count or match length; editing `event.duration`
afterwards does **not** re-derive the schedule on its own.

### `PATCH /events/:id/teams/:teamId`

Assigns (or re-assigns) one team's roster, replacing it wholesale. Optionally
renames the team in the same call. Rejected with `400` when a player is not
joined, is listed twice, or is **already in another team** — the message names
that team, since two teams claiming one player would corrupt standings and
per-player stats.

`EventPlayer.team` is kept in step automatically, so player-facing reads stay
consistent with the team documents.

### `GET /events/:id/teams`

The event's teams with players populated. Also attached to `GET /events/:id`.

### `POST /events/:id/shuffle` still works

Now a convenience wrapper over the two steps: it generates the teams and deals
the joined players across them in one call. Takes no body, so it uses the event's
`teamCount` and derives a match duration from the event.

### Fixtures are truncated, not just generated

Still a double round-robin, but cut to the number of matches the duration allows.
Truncation takes a **prefix** of the round-robin, and leg 1 is emitted in full
before leg 2 — so in a partial schedule every team meets a different opponent
before anyone plays a rematch.

## New `Team` collection

Per the spec note. `Team { eventId, groupId, name, players[], duration, status,
createdAt, updatedAt }`.

Its own collection rather than a string on `EventPlayer` because a team now
carries state a bare name could not: a per-team `duration` that drives the
schedule, and a `status` (`pending` until players are assigned, `ready` after).
`groupId` is denormalised from the event so a group's teams can be listed without
joining through events.

Unique index on `{eventId, name}`; a second on `groupId`.

## Breaking changes

| Change | Effect on the client |
|---|---|
| `group.rules` is a **string** | `List<String>.from(j['rules'])` **crashes**. A `rules.join('\n')` silently renders nothing. The Dart model in the groups doc is updated. |
| `PUT /events/:id/teams` is **gone** | Returns 404. Use `POST /teams/generate` then `PATCH /teams/:teamId`. |
| `GET /events/group/:groupId` hides expired | A history screen relying on this route now shows nothing for past events until it passes `includeExpired=true`. |

`vice-captain` is **additive** — no client breaks, but a build with a hardcoded
role list (`['owner','admin','captain']`) will not grant it the permissions the
API does. The Dart snippets in the groups doc are updated.

`POST /events/:id/shuffle` keeps its URL and still works, but its response shape
changed with the new flow.

## Not done

- **Tournament teams** are untouched. `TournamentTeam` is a separate collection
  with its own shape, and nothing creates `TournamentMatch` yet — out of scope
  here.
- **`event.duration` does not re-derive an existing schedule.** Editing it after
  generating teams leaves the fixtures alone; regenerate to pick up the change.
  Flagged rather than fixed, since silently rewriting a schedule an organizer may
  have already shared is worse than requiring the explicit call.
