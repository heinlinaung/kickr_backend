## ⚠️ Before deploying — run the migration

`before_match` was removed from the lifecycle enum. Any event still holding it
would be **stranded**: the new enum does not accept the value, so it fails
validation on the next save and `canTransition` refuses every move out of it.

```bash
npx ts-node scripts/migrate-remove-before-match.ts           # dry run, writes nothing
npx ts-node scripts/migrate-remove-before-match.ts --apply
```

Maps `before_match → preparation`, **forwards, not back to `join`**.
`before_match` meant "registration closed", and `preparation` is the state that
now carries that — join and leave are both refused there. Sending those events
back to `join` would silently reopen registration the organizer had closed.

Verified on seeded data: two stranded events moved, a `join` event untouched,
and a second pass reports nothing to migrate.

## 1. `before_match` removed from the lifecycle

```
before:  join → before_match → preparation → playing → after_match → done
after:   join → preparation → playing → after_match → done
```

It gated nothing of its own — join and leave were refused in `before_match` and
in `preparation` alike, and no action was permitted in one but not the other. So
closing registration and starting team assignment are now a single step.

- `join → preparation` is the first transition.
- **`preparation → join` reopens registration**, absorbing what
  `preparation → before_match → join` used to do. It is the only reverse edge.
- `PATCH /events/:id/status` with `"before_match"` now returns `400`
  (`Unknown status 'before_match'`), and the schema enum rejects it too.

The lifecycle spec transcribes the transition table independently of the
implementation and asserts **every** ordered pair — 25 of them now — so this
change could not land without the transcription being updated to match. That is
what caught it.

## 2. Shuffle and `event.teamCount` — no bug found

Reported as "shuffle always makes 4 teams, ignoring `teamCount`". It does not:
`shuffleTeams` reads `event.teamCount` and always has
(`events.service.ts`, `Math.min(event.teamCount ?? 4, joined.length)`).

Verified directly against MongoDB rather than by reading the code — an event
with `teamCount` 2, 3, 5 and 6 produced 2, 3, 5 and 6 teams respectively.

**Why it looked hardcoded:** `teamCount` **defaults to 4** on the Event schema.
An event created without setting it shuffles into 4 teams, which is
indistinguishable from a hardcoded 4 unless you set the field. Set `teamCount`
at create time or via `PATCH /events/:id` to change it.

One real cap does apply: with fewer joined players than `teamCount`, the count
is reduced to the player count — 6 teams with 3 players would leave 3 empty
teams, each generating fixtures they could never play.

## 3. `numberOfPlayers` is now enforced on assignment

`PATCH /events/:id/teams/:teamId` rejects a roster **larger** than the team's
`numberOfPlayers`:

```
400  Red holds at most 3 player(s); received 4. Regenerate the teams with a
     larger numberOfPlayers to raise the limit.
```

This reverses the decision recorded on 2026-08-13, where the field was a display
target that assignment did not check. It is now a hard upper limit.

**Under-filling stays legal.** A roster is built up incrementally, so "1/3
assigned" is a normal intermediate state, not an error — only exceeding the
limit is refused.

Two details:

- The limit is still **not** checked against the joined roster at generation
  time. 6 joined players with `numberOfPlayers: 11` is accepted; the limit only
  binds when players are actually assigned.
- `POST /events/:id/shuffle` cannot trip its own cap. It derives
  `numberOfPlayers` as `ceil(joined / teams)`, and the round-robin deal gives
  the largest team exactly that — checked exhaustively for 1–40 players across
  2–6 teams before relying on it.

## 4. `POST /events/:id/matches` — add a fixture by hand

New endpoint, organizer only. The generated schedule sometimes cannot express
what an organizer wants: 3 teams in a 60-minute event with 30-minute matches
fits `floor((60-10)/30)` = 1 match, so one team gets no fixture. This adds one.

```
POST /events/:id/matches   { "teamA": "Blue", "teamB": "Red" }
```

Deliberately narrow, by request:

- **No round-robin check** — `matches[]` may stop being a valid double
  round-robin. Standings still compute, since the fold is defined over the
  fixtures as stored.
- **No duration budget check** — scheduled minutes may exceed `event.duration`.
- **No renumbering**, and **no lifecycle gate**.

What it does still enforce, because the alternative is silent corruption:

- Both team names must belong to the event. The name **keys** the fixture, so a
  typo would create a match against a phantom team that quietly appears in
  standings. Casing is normalised to the stored team name.
- A team cannot play itself.
- `matchNumber` is server-assigned (`highest + 1`). It is uniquely indexed per
  event, so a caller-supplied value would risk a duplicate-key error on a
  number they cannot see.

Scores are not accepted at creation — a fixture starts unplayed and is scored
through the existing `PATCH`, so there is one way to write a result.

> ⚠️ `POST /teams/generate` and `/shuffle` both replace the fixture list
> wholesale, so a hand-added match is lost. Add after generating.

## 5. Referees can enter match scores

From the 2026-08-20 requirements doc, which lists "edit match results" under the
Referee flow. Until now `referee` was a label carrying exactly what `member`
does, so a referee got `403` from
`PATCH /events/:id/matches/:matchNumber`.

`referee` is now accepted **there and nowhere else**:

| Action | owner / admin | referee |
|---|---|---|
| Enter a match score | ✅ | ✅ |
| Edit/delete the event, transition it, generate teams, upload | ✅ | ❌ |

Implemented as a separate `assertCanScore` rather than by widening the shared
`assertOrganizer`: that helper guards **twelve** call sites, so adding `referee`
to it would have handed the role event deletion, lifecycle control and uploads
along with scoring. `assertOrganizer` now takes an allowed-roles list defaulting
to `['owner','admin']`, and scoring passes `['owner','admin','referee']`.

The lifecycle gate is unchanged — a referee can only score during `playing` or
`after_match`, same as an organizer.

A test asserts the boundary from the other side: a referee calling
`generateTeams`, `setStatus` and `remove` must still be refused. If `referee`
is ever added to `ORGANIZER_ROLES` by mistake, that test fails.

## 6. `country` / `city` are stored lowercase

From the 2026-08-20 doc: "country and city values should be stored in
lowercase". They were free text with only `trim: true`, so `"Thailand"`,
`"thailand"` and `"THAILAND"` were three distinct values.

Normalised in two places, deliberately both:

- **Schema** (`Group`, `User`) — `lowercase: true`, so a raw model write is
  normalised too, not just requests that pass through a DTO.
- **DTO** (`CreateGroupDto`, `UpdateGroupDto`) — a `@Transform` that trims and
  lowercases, so the value is canonical before it reaches the service and the
  Swagger examples match reality.

`GET /events?region=` now lowercases its input and does an **exact match**
instead of building a `/^…$/i` regex. Two gains: the `{country, city}` index
can actually be used (a case-insensitive regex cannot use it), and there is no
user input embedded in a regex at all, so `escapeRegex` is gone.

> **Correction to an earlier claim.** I described `?region=` as a live
> case-sensitivity bug. It was not — the old code already used an `/i` regex,
> so matching worked. The real problem was the storage layer: three spellings
> of one city as three distinct values, which breaks grouping and any future
> exact-match query. The filter change is a simplification that follows from
> normalising storage, not a bug fix.

**Not validated against an enum.** The doc asks for country/city to be checked
against reference data, but no such list exists in the repo and inventing one
would reject legitimate values the moment someone adds a city. Free text stands;
adding an enum later is additive and needs no migration.

### Migration

```bash
npx ts-node scripts/lowercase-country-city.ts           # dry run
npx ts-node scripts/lowercase-country-city.ts --apply
```

Mongoose only normalises on write, so a document not touched again keeps its
original casing forever. Covers both Group and User. Verified on seeded data:
mixed case normalised, surrounding whitespace trimmed, already-lowercase and
field-less documents skipped, re-run a clean no-op.
