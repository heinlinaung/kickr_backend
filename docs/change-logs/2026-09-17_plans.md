# 2026-09-17 — plans (default plan limits)

## What changed

Users are now on a **plan** that limits what they can create. One plan exists:

| Limit | default |
| --- | --- |
| Groups owned | **2** |
| Events created per calendar week | **3** |
| Photos in a group's gallery | **50** |

## Where it lives

- `src/plans/plans.ts` — the pure registry (`PLANS`, `planLimits()`,
  `weekOf()`). Limits are code, not database rows: every limit needs an
  enforcement site, so a new plan is a code change anyway.
- `User.plan` (new field, default `'default'`) — which plan a user is on.
  `planLimits()` maps an unknown/missing value to the default plan, so
  nothing degrades to unlimited. No API writes it yet; rows change by hand
  until billing exists.
- `PlansService` (`PlansModule`, a leaf module) — resolves a user's limits
  (`limitsFor`) or a group owner's (`limitsForGroupOwner`).

## Enforcement

- **Groups owned — `POST /groups`** (`GroupsService.create`): counts groups
  with `ownerId = caller`; at the cap it 400s ("Your plan allows owning at
  most 2 groups — delete one to create another"). Memberships of other
  people's groups are not metered.
- **Events per week — `POST /events`** (`EventsService.create`): counts the
  CREATOR's events whose `date` falls in the UTC Monday-start week of the new
  event's date. Metered on the event's date, not creation time — the limit is
  on how full a week gets. Deleting an event frees its slot; a `done` event
  still occupies one.
- **Gallery photos — photo upload** (`PhotosService.add`): the group's
  gallery (its own photos **plus its events'**, exactly what
  `GET /groups/:id/photos` shows) is capped by the group OWNER's plan. The
  cap applies to group uploads and to event uploads carrying a `groupId`; at
  the cap the 400 says to delete existing image(s) first. Counted before the
  upload, so a refusal never reaches ImageKit.
  - The old 30-photos-per-target cap now applies to **non-group** targets
    only (events, tournaments); a group's own photos are governed by the
    gallery cap instead, since 30 would stop a group ever reaching its 50.

## Notes

- No migration needed: existing users read as `plan: 'default'` via the
  schema default, and existing over-limit data is untouched — the caps gate
  new creation only.
- The admin test-data seeder (`POST /admin/test-data`) creates through the
  real services, so repeated runs reusing the same owner can now hit the
  group/event caps; clean up old runs between seedings.
- Client impact: expect 400s with the messages above on group create, event
  create, and photo upload when a cap is hit.
