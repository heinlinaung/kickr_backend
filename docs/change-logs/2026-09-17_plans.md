# 2026-09-17 — plans (default plan limits, `plans` collection)

## What changed

Users are now on a **plan** that limits what they can create. Two plans exist,
stored in the new `plans` collection (seeded by `scripts/seed-plans.ts`):

| Limit | default | no-limit-plan |
| --- | --- | --- |
| Groups owned | **2** | unlimited |
| Events created per calendar week | **3** | unlimited |
| Photos in a group's gallery | **50** | unlimited |

`no-limit-plan` exists for testing and admin accounts. Nothing assigns it —
set `User.plan` to `'no-limit-plan'` by hand.

**Deploy step: run `npx ts-node scripts/seed-plans.ts --apply`.** An unseeded
database is safe but strict: everyone (no-limit users included) gets the
default limits from the in-code fallback until the seed runs.

## Where it lives

- `plans` collection (`src/plans/schemas/plan.schema.ts`) — one row per plan:
  `name` plus the three limits. A limit of **`null` means unlimited**
  (resolved to Infinity, so `count >= limit` never trips); a MISSING field is
  not unlimited — it falls back to the default plan's value, so a half-seeded
  row degrades tight, never open. Tuning a limit or adding a plan is a seed
  edit + re-run, not a deploy.
- `src/plans/plans.ts` — the pure parts enforcement is written against:
  `PlanLimits`, `DEFAULT_PLAN_LIMITS` (the unseeded-database fallback — keep
  equal to the seed's default row), `resolveLimit()`, `weekOf()`.
- `User.plan` (new field, default `'default'`) — which plan a user is on, as
  a plain name string (not a ref). PlansService maps an unknown/missing value
  to the default plan, so nothing degrades to unlimited. No API writes it
  yet; rows change by hand until billing exists.
- `PlansService` (`PlansModule`, a leaf module) — resolves a plan's limits
  from the collection (`limitsByName`), a user's (`limitsFor`), or a group
  owner's (`limitsForGroupOwner`).

## Enforcement

- **Groups owned — `POST /groups`** (`GroupsService.create`): counts groups
  with `ownerId = caller`; at the cap it 400s ("Your plan allows owning at
  most 2 groups — delete one to create another"). Memberships of other
  people's groups are not metered.
- **Events per week — `POST /events`** (`EventsService.create`): counts the
  CREATOR's events whose `date` falls in the UTC Monday-start week of the new
  event's date. Metered on the event's date, not creation time — the limit is
  on how full a week gets. Deleting an event frees its slot; a `done` event
  still occupies one.
- **Gallery photos — photo upload** (`PhotosService.add`): the group's
  gallery (its own photos **plus its events'**, exactly what
  `GET /groups/:id/photos` shows) is capped by the group OWNER's plan. The
  cap applies to group uploads and to event uploads carrying a `groupId`; at
  the cap the 400 says to delete existing image(s) first. Counted before the
  upload, so a refusal never reaches ImageKit.
  - The old 30-photos-per-target cap now applies to **non-group** targets
    only (events, tournaments); a group's own photos are governed by the
    gallery cap instead, since 30 would stop a group ever reaching its 50.

## Notes

- Existing users read as `plan: 'default'` via the schema default, and
  existing over-limit data is untouched — the caps gate new creation only.
  The only migration is the plans seed above.
- The admin test-data seeder (`POST /admin/test-data`) creates through the
  real services, so repeated runs reusing the same owner can now hit the
  group/event caps; clean up old runs between seedings.
- Client impact: expect 400s with the messages above on group create, event
  create, and photo upload when a cap is hit.
