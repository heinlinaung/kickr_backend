# 2026-10-24 — Awards: MVP, Group Challenge and memories

Awards go either to one player for one event (**MVP**) or to a whole group
for winning a challenge (**Group Challenge**). A group award lives under the
group; each eligible member can add it to their own profile as a **memory**.

| Award type        | Recipient | Given for                       | Shows in                                                  |
| ----------------- | --------- | ------------------------------- | --------------------------------------------------------- |
| `MVP`             | Player    | Best player of one event        | Player's Awards tab                                       |
| `GROUP_CHALLENGE` | Group     | The group won a challenge match | Group's Awards tab; a player's Awards tab once a memory   |

All responses below are the payload inside the standard `{ "data": … }`
envelope. All endpoints require a JWT. IDs are Mongo ObjectIds.

---

## Endpoints

| Method       | Path                                          | Who                | Purpose                         |
| ------------ | --------------------------------------------- | ------------------ | ------------------------------- |
| GET          | `/events/:id/awards/mvp`                      | Group owner/admin  | The event's MVP award           |
| POST / PATCH | `/events/:id/awards/mvp`                      | Group owner/admin  | Give the MVP award              |
| DELETE       | `/events/:id/awards/mvp`                      | Group owner/admin  | Take back the MVP award         |
| GET          | `/users/:userId/awards`                       | Anyone who can see the profile | A player's Awards tab |
| GET          | `/groups/:groupId/awards`                     | Approved member    | A group's Awards tab            |
| POST         | `/groups/:groupId/awards/:awardId/memories`   | Eligible member    | Add a group award to my profile |
| DELETE       | `/me/memories/:memoryId`                      | Self               | Remove a memory from my profile |

There is no endpoint to create a Group Challenge award: the system creates it
(see below).

### Who may use `/events/:id/awards/mvp`

Every method (GET, POST, PATCH, DELETE) is limited to an **approved owner or
admin of the event's group**: either group on a challenge event. The event
creator gets no access just for being the creator, unlike other organizer
actions. An event without a group has no owner or admin, so its creator
remains the only one allowed. Anyone else → `NOT_EVENT_ORGANIZER`.

### `GET /events/:id/awards/mvp`

`200` with the same shape as the POST response below, or `null` when no MVP
has been given yet.

### `POST /events/:id/awards/mvp` (and `PATCH`)

```json
// Request
{ "userId": "665f…200", "note": "2 goals, 1 assist" }

// 201 Created (PATCH: 200)
{
  "id": "6710…0a",
  "type": "MVP",
  "recipient": { "kind": "USER", "id": "665f…200" },
  "eventId": "6705…55",
  "title": "MVP – Sunday Football",
  "note": "2 goals, 1 assist",
  "awardedBy": "665f…001",
  "awardedAt": "2026-10-18T12:00:00.000Z"
}
```

- Allowed once the match is over: `after_match` **or** `done`.
- `note` is optional, max 300 chars.
- One MVP per event. Same `userId` again → updates `note` only. A different
  `userId` → `MVP_ALREADY_AWARDED`; DELETE first.
- The player is notified when they receive it.
- `event.result.mvpUserId` follows the award. `mvpGoal`/`mvpAssist` are kept
  when the MVP is the same player and cleared when it changes.

### `DELETE /events/:id/awards/mvp`

`204`. Removes the award from the player's Awards tab and clears
`mvpUserId`/`mvpGoal`/`mvpAssist` off the result. The score is kept.

### `GET /users/:userId/awards`

Query: `type=MVP|GROUP_CHALLENGE` (optional), `limit` (1–50, default 20),
`cursor`. The player's own MVP awards plus group awards they added as
memories, newest first.

```json
{
  "items": [
    {
      "id": "6710…0a",
      "type": "MVP",
      "source": "OWN",
      "title": "MVP – Sunday Football",
      "note": "2 goals, 1 assist",
      "event": { "id": "6705…55", "title": "Sunday Football" },
      "awardedAt": "2026-10-18T12:00:00.000Z"
    },
    {
      "id": "6710…20",
      "type": "GROUP_CHALLENGE",
      "source": "MEMORY",
      "memoryId": "6711…03",
      "title": "Second FC vs Aura Bangkok – Winner",
      "group": { "id": "68aa…09", "name": "Second FC", "deleted": false },
      "awardedAt": "2026-10-01T00:00:00.000Z"
    }
  ],
  "nextCursor": null,
  "hasMore": false
}
```

- `source`: `OWN` = earned by this player, `MEMORY` = a group award they chose
  to show.
- **Visibility.** There is no friends feature in this backend yet, so the
  gate matches `GET /users/:id/summary`: a missing, deleted or private account
  returns `404`, except to the user themselves. Narrow it to friends once
  friends exist.
- `group.deleted: true` → the group is gone. `name` is then the name the
  award was won under.

### `GET /groups/:groupId/awards`

Query: `limit`, `cursor`. Approved members only. Same page shape. Each item:

```json
{
  "id": "6710…20",
  "type": "GROUP_CHALLENGE",
  "title": "Second FC vs Aura Bangkok – Winner",
  "challenge": { "id": "68cc…01", "title": "Second FC vs Aura Bangkok" },
  "event": { "id": "68dd…01", "title": "Second FC vs Aura Bangkok" },
  "awardedAt": "2026-10-01T00:00:00.000Z",
  "memoryId": null,
  "canAddAsMemory": true
}
```

Challenges have no title of their own, so `challenge.title` is the title of
the challenge's match event.

### `POST /groups/:groupId/awards/:awardId/memories`

No body. `201` → `{ "memoryId": "6711…03", "awardId": "6710…20" }`.

- Eligible = the caller **played for the winning group in the challenge
  match** (a `joined` roster row on that side) **and was an approved member
  of the group when the award was given**. That list is frozen on the award,
  so leaving the group later does not remove eligibility, and joining
  afterwards does not grant it.
- Once per award per user.

### `DELETE /me/memories/:memoryId`

`204`. Only the caller's profile changes; the group's award is untouched.
Another user's memory id answers `MEMORY_NOT_FOUND`.

## Group Challenge award: when it is created

When a **challenge event moves to `done`** (`PATCH /events/:id/status`), the
system finds the winner:

1. From the overall result, `POST /events/:id/result`: `scoreA` is the
   challenger side and `scoreB` the challenged side (the challenger's team is
   always generated first).
2. If no overall score was posted: from the goals summed across the played
   fixtures between the two teams (named by the agreed kit colors).

- **A draw, or no score at all, gives no award.**
- Every eligible player is notified ("Challenge won! … add the award to your
  profile").
- At most one award per challenge (unique index). A failure here is logged
  and never blocks the `done` transition.

## Rules

- Leaving a group does **not** remove memories already added.
- If a group is deleted, its awards stay visible as memories on players'
  profiles with the group's name as it was at award time.
- Taking back an MVP removes it from the player's Awards tab.

## Error codes

Error bodies carry a machine-readable `code` next to `message`:

```json
{ "statusCode": 409, "code": "MVP_ALREADY_AWARDED", "message": "…", "timestamp": "…", "path": "…" }
```

| Code                      | HTTP | When                                                              |
| ------------------------- | ---- | ----------------------------------------------------------------- |
| `NOT_EVENT_ORGANIZER`     | 403  | `/events/:id/awards/mvp` called by someone not group owner/admin  |
| `USER_NOT_IN_EVENT`       | 400  | The MVP did not join the event                                    |
| `MVP_ALREADY_AWARDED`     | 409  | The event already has a different MVP                             |
| `EVENT_NOT_FINISHED`      | 400  | Event is not `after_match` or `done`                              |
| `AWARD_NOT_FOUND`         | 404  | No MVP to take back; award not under that group; malformed id     |
| `NOT_ELIGIBLE_FOR_MEMORY` | 403  | Caller is not on the award's eligibility list                     |
| `MEMORY_EXISTS`           | 409  | Caller already added this award                                   |
| `MEMORY_NOT_FOUND`        | 404  | No such memory on the caller's profile                            |
| `NOT_GROUP_MEMBER`        | 403  | Group Awards tab read by a non-member                             |

Validation failures (bad body, bad `type`, bad `cursor`) stay plain `400`s
without a `code`, like the rest of the API. An unknown event, group or user
is a plain `404`.

## Legacy `POST /events/:id/mvp`: unchanged contract

It still takes `{ userId, goal, assist }`, still runs only in `after_match`,
and still lets the organizer replace the MVP in one call. It now also keeps
the MVP award in step: it gives the award, or swaps it to the new player.

## Data

**`awards`**: `type` (`MVP` | `GROUP_CHALLENGE`), `recipientKind` (`USER` |
`GROUP`), `recipientId`, `eventId`, `challengeId` (Group Challenge),
`title`, `note`, `eventTitle` and `groupName` (snapshots), `awardedBy`
(null = system), `awardedAt`, `eligibleUserIds` (Group Challenge).
Unique: `eventId` where `type: MVP`; `challengeId` where
`type: GROUP_CHALLENGE`.

**`awardmemories`**: `awardId`, `userId`, `createdAt`. Unique on
`(userId, awardId)`.

No migration. MVPs recorded before today have no award row and don't show on
Awards tabs until the organizer re-submits them.
